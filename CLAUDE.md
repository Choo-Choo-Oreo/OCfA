## Mod specific documentation
documentation/wikis/ contains two file sets, distinguishable by name:
- Wiki_*.txt: 50 official HOI4 wiki mirrors — community-sourced, tends to include usage
  examples, aliases, gotchas, and version-specific caveats that the dev docs omit.
- common_*_documentation.md and documentation_*_documentation.md: 49 developer-authored files —
  tends to be terser and more authoritative on exact signatures/arguments/availability.

These are not a clean split by topic. Some subjects are documented in both (e.g. console commands,
military_industrial_organization, on_actions) — check both when working in those areas, since each
adds something the other lacks. Special_projects and script_constants currently have no wiki-side
equivalent, so the dev doc is the only source there. Read the relevant file(s) when a task needs
it, do not load the whole folder.

### Resource prospecting import/export

`tools/IRP.import_resource_prospecting_to_csv.py`,
`tools/IRP.set_resource_prospecting_from_csv.py`

`IRP.resource_prospecting.csv` is the source of truth for this system --
edit the CSV directly for ongoing changes. `import_...to_csv.py` exists to
pull the ORIGINAL/legacy resource prospecting data (from the generated
`common/decisions/IRP.resource_prospecting.txt`) into that CSV format once;
`set_...from_csv.py` regenerates the decisions file from the CSV afterward.
The two scripts' parsing patterns (`BLOCK_RE` etc.) must stay in sync with
whatever template `set_...from_csv.py` emits -- a hand-edited decisions file
that doesn't match the expected block shape will be silently mis-parsed by
the importer rather than erroring clearly, so prefer editing the CSV over
hand-editing the generated `.txt`.

## Naming conventions
generic mod wide content, no country or system tie
Country tags: must match an entry in common/country_tags, never invented

Container files: TAG.category.txt or aNCFO.category.txt, dot separated,
      example HHE.ideas.txt, aNCFO.ideas.txt, category matches the
      containing folder in most cases, characters, decisions, ideas, etc

Internal script IDs: type_name for generic, example idea_communist_support
      TAG_type_name for country specific, example HHE_idea_communist_support
      the type token is included even on generic IDs, this makes every ID
      greppable by type across the whole codebase regardless of file or
      folder of origin

Exception, national focus: folder is national_focus, container files use
      national_branches instead (HHE.national_branches.txt), because one
      file holds multiple focus trees rather than one tree per file
      internal IDs shorten to focus (HHE_focus_communist_support), not
      national_branches or national_focus

Legacy naming exception: some older files predate the current naming
      standard and do not follow it consistently, particularly early
      national_branches files. Do not use an unfamiliar or older looking
      file as a pattern reference without checking it against the rules
      above first. When in doubt, MJU.national_branches.txt is a clean,
      current example of the standard to follow instead. Clarify with the user when you notice legacy files.
      when a file's structure does not match the established naming or format conventions, stop and describe the discrepancy rather than normalizing or guessing at the intended structure.

## General HOI4 Modding Reference

This section is not tied to mod specifically, it applies to any HOI4 mod worked on in this tool. Keep it below the mod specific block above so it can be copied into other mod projects with minimal edits.

### Generating and reading logs

When a new log is needed, run the "hoi4.exe" executable with the "-debug -crash_data_log" launch options, reproduce the issue, then close the game. Fresh logs are written to:
"C:\Users\Orea\Documents\Paradox Interactive\Hearts of Iron IV\logs"

Logs are overwritten every launch, so grab the relevant file immediately after reproducing the issue, before launching the game again. It takes about 60 seconds for the game to launch and generate a new set of logs, so wait for that window to pass before assuming a log has updated.

Priority order for reading logs after a crash or bug report, highest usefulness first:
- error.log: nonfatal errors, almost all entries touching the common folder should be fixed
- game.log: actions taken by countries in game, useful when a crash follows a specific action
- setup.log: completion of setup loading per step, very useful for pinpointing a loading crash
- memory.log: memory used during setup, useful for narrowing down when a loading crash happened
- time.log: time per loading step and tick interval, also useful for loading crashes
- ai.log / system_debug.log / text.log: medium usefulness, situational
- exceptions.log, ai_trace.log, graphics.log, and the command logs: low usefulness for most modding bugs

Each crash creates its own timestamped subfolder at:
"C:\Users\Orea\Documents\Paradox Interactive\Hearts of Iron IV\crashes\hoi4_XXXXXXXX_XXXXXX\meta.yml"
where each X is a digit. When investigating a crash, identify the most recently created "hoi4_" subfolder and read meta.yml from inside it, do not assume the top level crashes folder itself contains the file. Its LastRead line points to the file and line last read before the crash, for example "LastRead: map/supply_nodes.txt (727)". If that line is the last line of the file, the true failure is likely in the next file read instead, which is harder to pin down.

Observed once (2026-07-08, LastRead gfx/3dviewenv/plane_designer_model.txt), treat as a hypothesis to check, not a rule: a last-line LastRead can also mean the crash is a later resolution step choking on a bad cross-reference defined in an EARLIER file -- there, error.log showed common/units/air.txt:112 referencing the undefined airframe medium_plane_naval_bomber_airframe, and the LastRead file itself was an innocent static view config with no references in it. When the last-line case hits and the LastRead file looks reference-free, scan error.log backward for reference-resolution errors (Unexpected token, is not an equipment type, could not find, missing) before assuming the next-file-forward reading. crash_triage.py does this scan automatically.

Once a crash folder has been read and is no longer needed, clear that specific timestamped subfolder to the Windows recycle bin rather than deleting it permanently, and rather than clearing the entire crashes directory. This keeps older crash folders available for comparison if a new crash turns out to be related.

### Console commands reference

Two sources in documentation/wikis/, complementary rather than duplicates:
- console_commands_documentation.md: authoritative argument signatures and release-build
  availability, but terse — use it to confirm exact syntax and whether a command works outside
  debug builds.
- Wiki_ConsoleCommands.txt: community-sourced usage detail the dev doc omits — worked examples,
  aliases, gotchas (e.g. commands that silently don't do what their name implies), and notes on
  commands that stopped working in a specific version.

When a workflow step calls for the user to run a console command (e.g. "let the game run several
ticks under observe," "fire a specific event with the console"), check both before naming the
command: confirm exact syntax/availability from the dev doc, and pull any example/gotcha from the
wiki file if one exists, rather than stating the command from memory.

### Map connectivity tools

`tools/_map_common.py`, `_check_connectivity.py`, `_check_global_landmasses.py`

Shared library (`_map_common.py`) plus two analysis scripts that derive the
mod's land-adjacency graph directly from `map/provinces.bmp` pixel borders, not
from `adjacencies.csv` -- that file holds ONLY exceptions (straits, impassable
borders, canal/tunnel passages), never standard land borders. Assumes only
standard HOI4 map/history file structure -- portable to any mod as-is.

`_check_global_landmasses.py` computes every discrete landmass on the map,
ownership-independent, via connected components over all land provinces.
Writes `landmasses.json`: each landmass's province list, the states on it, and
each state's current owner. Flags states whose provinces span more than one
landmass as worth a manual check (a real offshore island looks identical here
to an accidental stray province).

`_check_connectivity.py` takes a country tag and groups that country's owned +
cored states into land-connected clusters using OWNED-territory-only
adjacency (core-only claims never bridge or merge clusters -- they always
report as isolated singletons, which is expected, not a bug). States outside
the largest cluster are flagged as candidates to verify for accidental
exclaves, not confirmed detached territory. Also reports straight-line
pixel distance from each state to the capital (explicitly NOT a route
distance -- ignores terrain and sea travel). Writes `connectivity_TAG.csv`,
optionally `connectivity_TAG.json` with `--json`.

Both scripts resolve all paths from their own location (mod root = parent of
`tools/`) and refuse to run if that root doesn't look right (no
`descriptor.mod`, no `map/` or `history/states/`), so a moved/copied script fails
loudly instead of silently operating on the wrong directory.

Usage: `python tools/_check_connectivity.py TAG [--json] [--conn 4|8]`
       `python tools/_check_global_landmasses.py [--conn 4|8]`
Requires: Pillow, numpy.

Useful for: verifying a state's owner assignment didn't accidentally create
a physically disconnected holding, and for cross-referencing a numeric
state/province id against its landmass and owner without loading the game.
See "State/region ID readability" below for pairing this with actual names.

### State/region ID readability

`tools/rename_states_to_loc_names.py`, `rename_regions_to_loc_names.py`

Purpose: `history/states` and `map/strategicregions` files are named by numeric
ID by default. Without a resolved name in the filename, a bug report like
"state 951 has an issue" gives no context without loading the game and
checking in-game or cross-referencing tags manually. These scripts rename
each file to `ID-<resolved localised name>.txt` via `git mv` (tracked, not a
silent OS rename), resolving the file's declared `name = "KEY"` against the
actual localisation `.yml`s. Already-correct names are skipped; unresolvable
keys are reported, not guessed at or silently left broken. Assumes only
standard HOI4 file/localisation structure -- portable to any mod as-is.

Run after adding/renaming states or regions, or after loc changes that would
change a resolved name, so filenames stay a usable reference for anyone
(including Claude Code) reading a bug report that cites a bare ID.

### Common crash causes by phase

Claude Code cannot click through country selection or play out the middle game as a human would
(specific decisions, manual diplomatic actions, arbitrary country choice). It CAN exercise
AI-driven midgame play unattended via tools/soak_test.py (see below), which covers the
client_ping/hourly_tick class of bugs listed below without requiring the user to reproduce them
by hand.

Main menu loading:
- common/countries/cosmetic.txt: usually a full overwrite of common/national_focus/ or common/continuous_focus/
- map/rocketsites.txt: usually a full overwrite of history/states/ or common/unit_leader/, since there is no generic fallback for states
- common/national_focus/*.txt: often a shared_focus or joint_focus reference to a focus that does not exist
- gfx/models/supply/railroad.shader: usually a malformed map bitmap, dimensions not divisible by 256, a bitmap over 40 MiB, mismatched dimensions between bitmaps, or a wrong DIB header
- history/general or history/countries files, or map/rocketsites.txt: a victory_points entry pointing at a province that does not exist
- savegame.hoi4 or map/cities.txt: too many defined countries relative to available dynamic country slots, typically in the 40 to 80 range, often from a reckless overwrite of common/country_tags

During country selection (requires the user to perform the action in game and report back):
- set_controller: a bookmark country missing a valid capital in its history/countries/TAG file
- history/units files: a naval OOB with airwings defined directly on a carrier, pre 1.12 syntax
- history/units files or map/railways.txt: a division template with no matching common/ai_templates entry
- map/supply_nodes.txt or map/railways.txt: a supply building placed on a province not inside any state
- tutorial/tutorial.txt: an erroneous tutorial file, replacing its contents with an empty tutorial block usually fixes it

Middle of the game:
- client_ping or hourly_tick: almost always AI related. Try tools/soak_test.py first — it
  exercises AI ticks unattended and can surface these directly. Only fall back to asking the user
  to reproduce manually (disabling AI via console) if the soak test doesn't catch it. Common
  causes: a division template with no matching ai_templates entry, a state with no owner defined
  in its history file, or an incomplete map/buildings.txt affecting naval base or floating
  harbour placement.

### Automated crash triage

`tools/crash_triage.py` runs the manual procedure above as a script: it
finds the most recent hoi4_* crash folder, parses meta.yml LastRead, prints
the priority-ordered logs, and matches LastRead against the "Common crash
causes by phase" table, printing candidate causes as suggestions. It flags
(rather than guesses) the ambiguous cases CLAUDE.md calls out: no meta.yml,
an unparseable LastRead, and LastRead sitting on the last line of its file
(true failure likely in the next file read). Defaults to the real crashes/
logs/mod/base-game paths; run `python tools/crash_triage.py --help` for
flags (`--crash-folder`, `--logs-source`, `--lines`, `--no-logs`).

### Automated soak test

`tools/soak_test.py` runs the mod unattended via `-hands_off` (auto-starts
unpaused at max speed with human AI; this mod's defines re-point
HANDS_OFF_START_TAG to LLA) to surface crashes/errors that only appear over
extended play. It snapshots error.log and game.log to a timestamped folder
under the HOI4 documents dir every few minutes during the run (logs are
overwritten each launch, so end-only capture loses transient errors), stops
and hands off to crash_triage.py if a new hoi4_* crash folder appears, and
ends with a summary of errors per snapshot including which appeared mid-run.
Defaults: 60 min, snapshot every 5 min; `python tools/soak_test.py --help`.
Scope limits: it exercises AI-driven play only — it can catch loading errors,
AI/tick (client_ping / hourly_tick class) crashes, and script errors the AI
triggers, but NOT human-only UI paths, specific manual decisions or
diplomatic actions, or selection of arbitrary countries. Those still require
the "user performs the action and reports back" workflow above.

### Project tree snapshot

`tools/find_tree.py` writes a plain-text indented tree of any directory
(default: the mod root) with `--depth`, `--ignore`, and `--output` options.
It default-ignores VCS internals, the binary asset dirs (gfx, music, sound),
and simple patterns from the root .gitignore (which covers the embedded
2993766165 reference mod), and lists everything it pruned on stderr. It
supersedes localisation/_find_tree.py, which only dumped its own folder.

### General debugging workflow

1. Clean the error log before testing, some errors look harmless but still cause the crash.
2. Reproduce with "-debug -crash_data_log" active, then check meta.yml LastRead alongside error.log and game.log.
3. If replace_path is involved, remember both .mod files need matching entries for it to apply, and unloading a folder without porting its generic files over is a frequent crash source.
4. If the last read file is not conclusive, use a binary search approach: temporarily strip large chunks of files from the mod and reintroduce them in halves until the crashing set is isolated.
5. After a major game patch, check the patch notes for an "Important modding notes" section, it usually lists breaking changes that need fixing.
6. Keep an override file in common/defines, letting defines fall through to the base game is a common source of crashes after minor updates.
7. Track changes with git or another version control system so a working revision can always be found again.

### Error backlog

documentation/_error_backlog.md is the log of record for fixes found via
automated testing (crash_triage.py, soak_test.py). Each entry: what was
wrong (with mechanism, not just symptom), what changed, and how it was
verified (before/after run names or error counts, not just "fixed").
Still-open items get their own section rather than being dropped.

Prefer this file over in-code comments for explaining a fix. A short note
is fine where the reasoning genuinely isn't obvious from the diff itself
(e.g. "swap back if X is added later"), but default to keeping the code
itself clean and putting the explanation in the backlog file instead of
narrating history inline.
